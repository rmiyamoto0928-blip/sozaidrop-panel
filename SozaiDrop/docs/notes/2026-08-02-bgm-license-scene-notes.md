# SozaiDrop ③をフリー/楽曲・場面・内訳の3段ボタンに——計画から変えたこと

2026-08-02 ／ 触ったのは `js/main.js` `index.html` `css/style.css` `test/harness.html` の4つだけ。
設計（タグの決め方・3段の出し分け・件数の束ね方）は承認どおりで変えていない。
以下は**設計に書かれていなかったので実装時に決めたこと**だけを残す。

## 1. 「−フォルダ」を選択ダイアログ方式に変えた

- 変えたこと: これまで `#folderSelect` で選んでいた「解除するフォルダ」を、`＋フォルダ` と同じ
  フォルダ選択ダイアログ（`chooseFolder()`）で名指ししてもらう方式にした。2回目の押下では
  ダイアログを出し直さない（`removeArmedRoot` / `removeArmedPicked` に覚えておく）。
- 理由: ③からフォルダのプルダウンが無くなったので、「いま選んでいる登録フォルダ」という
  入力源そのものが消えた。ボタンだけ残すと押しても何も指せない。
- ついでに消えたもの: 旧実装にあった「②プロジェクト内では解除できません」の門番。
  ③がフォルダを指さなくなり、②の状態と解除対象が無関係になったため。
- サブフォルダを選ばれたときは最長一致の親（＝登録フォルダ）を対象にし、選んだものと
  対象が食い違うときだけ何が外れるかを名指しで断る。

## 2. プロジェクト直下の素材の場面名を `プロジェクト直下` にした

- 変えたこと: `PROJECT_ROOT_SCENE = 'プロジェクト直下'`（`js/main.js`）。ビンに入っていない
  素材の場面名に使う。
- 理由: 設計はPCフォルダ側の「直下は登録フォルダ名を場面にする」しか決めていなかった。
  プロジェクト側には登録フォルダ名にあたるものが無く、空文字にすると名無しのボタンが出る。
  実機のJSXは先頭にプロジェクト名を置くので通常は到達しないが、無防備にはしない。

## 3. ④の見出しが「場面（／内訳）」だけになり、同名の登録フォルダは1グループに融合する

- 変えたこと: `groupKey()` / `groupLabel()` から登録フォルダのフルパス・表示名を外し、
  場面と内訳だけで作るようにした（キーは `F:` / `P:` の接頭辞で②の場所だけ分ける）。
- 理由: ③が「ポップは登録フォルダをまたいで1つのボタン」に束ねる仕様なので、④だけ
  登録フォルダ別に割れていると、ボタンの件数と見出しの件数が合わなくなる。
- 影響: `/A/SE` と `/B/SE` を両方登録したときの④は1グループになる（旧C-23の意図が反転）。
  `rootLabel()`（同名ルートに親名を添える）は登録・解除・行方不明の通知では今までどおり使う。
  テストは削除せず、新しい意図（1グループに束ねる・通知では見分けが付く）に書き換えた。

## 4. `index.html` の③場面の段に `id="sceneStep"` を足した

- 変えたこと: `<div class="fstep" id="sceneStep">`。
- 理由: 3-a と 3-c は `.fstep.hidden` で段ごと消す作りにしたので、3段とも同じ流儀で
  「段が出ているか」を1か所（`#〜Step`）で判定できるようにするため。id が無いと
  検査側が場面の段だけ別の探し方をすることになり、実際に見落としが出た。

## 5. 旧設定ファイルの `prefs.folder` は読まずに捨てる

- 変えたこと: `restorePrefs()` は `p.folder` を一切見ない。`license` / `scene` / `sub` だけ復元する。
- 理由: 旧 `folder` はフォルダのフルパスで、新しい ③ の意味（場面名）とは別物。
  無理に読み替えると当たらない場面名が入って毎回「すべて」に戻る挙動になるだけなので、
  最初から「すべて」で開く。落ちないことのほうが大事。

# 採点レビューの指摘7件（A〜G）を直したときに、指摘の「直し方」から変えたこと

## 6. C・F の検査は、既存のテスト用素材に足さず「専用セクション」を新設した

- 実際: どちらも**そのセクションの後ろにある4つのセクションが件数を直書きで持っている**

  それら全部の期待値がずれて、直した件数と本来の意図の区別が付かなくなる。
  そこで自前の設定でやり直す独立セクション（新41・新42）を足し、`PROJECT_RECORDS` は

- 指摘の直し方: 素の `querySelector()` を新セクション方式（`icon30` 等）に寄せる。
- 実際: 同じ「1件も出ていないと以降が全部打ち切られる」事故は

  そこで共通ヘルパー（`partOf` / `partText` / `iconOf` / `clickPart` / `pathOfName`）を足し、
  `click()` `fire()` `fireDrag()` は対象が無ければ**その場で1件だけ落として先に進む**ようにした。
  重複していた `icon30` / `icon34` は `iconOf` に統合（検査の中身は変えていない）。
- 通ったときは何も記録しないので、PASS の件数は増えない（緑のときの数は動かさない）。

## 8. G の「（直下）」は空文字ではなく専用の目印 `SUB_NONE` を値にした

- 事情: 3-c の値は空文字が「すべて（絞り込まない）」の意味で埋まっている。
  空文字を「内訳なし」に流用すると、すべてと区別が付かない。
- 実際: `SUB_NONE = '/直下'`（フォルダ名・ビン名に使えない `/` を頭に付けて実在の内訳名と
  ぶつからないようにした値）を作り、`inScope()` と `buildTagFilters()` の作り直し判定、
  設定ファイルへの保存・復元の4か所で同じ値を見るようにした。
- 並び順は件数順ではなく**必ず最後**に置く（実在の内訳名に混ざると探しにくいため）。

## 9. B の案内文が指す段の名前は、テスト側が画面の見出しから引いて突き合わせる

- 事情: 3-a の段には ③ のような番号が無く、見出しは `フリー/楽曲` という言葉そのもの。

- 実際: `licLabel()`（`#licStep .fnum` の実テキスト）を足し、案内文がその言葉を
  含んでいることを検査するようにした（`sceneLabel()` `sendKindWord()` と同じ流儀）。

## 21. R1 は「前回入れたHTMLを行に覚えさせる」方式にした（`innerHTML` とは比べない）

  **5件 FAIL**（同じ部品のまま×3・⟳後×1・長さ計測後×1）。戻して md5 一致。
- 検査は2系統: ①`buildTagFilters()` を無変化で呼んでも `select` ノードが同一オブジェクト

  「中身が変わったときはちゃんと作り直す」（止めすぎ防止）とフォーカス復帰も検査。

- 画面に出せる要素は **`contrastOk()` で実測する**のが原則。

## 37. 「たまたま通っていた」検査を、値の重複を直に見る検査に置き換えた（4周目レビュー・修正済み）
堅牢性担当が変異テストで実証した指摘。**修正済み・898項目に増加**。

**何が悪かったか**
- 新43（項目14）は `SUB_NONE = '直下'` に変異させると「4件 FAIL する」と書いていたが、
  3-c をプルダウン化したあとに実測すると **3件しか FAIL しない**。
- 原因は `pickTag()` が `sel.value = hitOpt.value`（＝**値**での指定）で選んでいたこと。
  `sel.value = …` は「値が一致する**最初の**選択肢」を選ぶ仕様なので、受け皿の値（`SUB_NONE`）と
  実フォルダ名がぶつかった状態では、狙った選択肢とは別のものが選ばれても気づけない。
- その結果、選択状態を見る2件（`選んだ項目が選択状態になる` / `そのときの選択状態も実フォルダのほう`）は、
  「ネイティブの `.value=` 代入（先頭一致）」と「`innerHTML` 再構築時のHTML解析（後勝ち）」の
  どちらが起きたかで**偶然**期待値と一致していた＝この変異に対して何も保証していなかった。

**直したこと（3か所）**
1. `pickTag()`: `sel.value = hitOpt.value` → **`hitOpt.selected = true`**（値ではなく選択肢そのものを選ぶ）。
   検査を動かす側が「自分が選んだと言っている物」を本当に選ぶようにした。
2. `dupTagValues(row)` を追加（`dupTagNames()` の隣）。選択肢の **value の重複**を返す。
3. 新43 に `内訳の選択肢に同じ値のものが無い（受け皿と実フォルダがぶつかっていない）` を追加。

**なぜ「値の重複」を見るのが正しいのか**
本体（`js/main.js` の `bindTagSelect`）は change のとき **`sel.value` しか見ていない**。
つまり値がぶつかった時点で、本体もテストも「どちらを選んだか」を原理的に区別できない。
選択状態という**間接的で不安定な指標**ではなく、**衝突そのもの**を見張るのが唯一確実な形になる。

**確認（コピーに対する変異テスト・本番は未変更）**
| 変異 | 結果 |
|---|---|
| なし（ベースライン） | ALL PASS 898 passed / 0 failed |
| `SUB_NONE = '/直下'` → `'直下'` | **FAILED 894 / 4**（3回連続で同じ＝確定的） |
| （同上）落ちる4件 | 先頭が `/` ／ **値の重複（新規）** ／ 実フォルダ選択時の中身 ／ `filter.sub === SUB_NONE` の判定 |
| メニューの色＋影を直書き（3周目修正の回帰確認） | FAILED 896 / 2（前回と同じ＝回帰なし） |

**【訂正・5周目レビューで実証】4件目を捕まえているのは `dupTagValues()` 単体で、`pickTag()` の変更ではない**
- 上の「直したこと1」が4件目の FAIL を生んだ、と読めるように書いていたが**これは誤り**。
  実測: `pickTag()` を旧実装（`sel.value = hitOpt.value`）に戻したコピーで同じ変異を流しても
  **新実装と一字一句同じ 894/4 FAIL**。`dupTagValues()` の検査だけを外すと新旧どちらのドライバでも **894/3**。
  ＝**4件目は `dupTagValues()` 単体の働き**で、`pickTag()` の変更は件数に寄与していない。
- なぜ選択状態の2件が新旧どちらでも通るのか（5周目レビューが突き止めた仕組み）:
  1回目の選択で `filter.sub` が `'' → '直下'` に変わり `setTagRow()` が再構築する。このとき
  `cur === value` が実フォルダ側と受け皿側の**両方**に当たって `selected` が2つ入り、
  HTML再解釈の「後に書かれた方が勝つ」規則で**常に**受け皿側が選ばれる。
  2回目の選択は `filter.sub` の値が変わらないため `row.sdTagHtml` のキャッシュで再構築が起きず、
  ドライバが直接いじった選択状態がそのまま残る（旧ドライバでも「先頭一致」がたまたま実フォルダを指す）。
  この2つの偶然が重なるため、**ドライバの実装に関係なく**選択状態の2件は通る。
- では `pickTag()` の変更は無意味だったのか＝**無意味ではない**。「値が一意である前提」を外した
  より厳密なドライバであり、新旧で 898件ベースライン・全変異の結果が完全一致＝**他のどの検査も弱めていない**。
  ただし「これが4件目を生んだ」という因果の主張は取り下げる。

**次に同じ間違いをしないための指針**
- **検査を動かす側（ドライバ）も検査対象**。「値で指定する」操作は、値が一意である保証が無いと嘘をつく。
- **「直したから件数が増えた」を実測せずに書かない**。増えた原因が別の変更だったという今回の事故は、
  旧実装に戻したコピーで同じ変異を流す（＝原因の切り分け）だけで防げる。
- 変異テストで期待した件数と実際の件数が違ったら、**実装ではなくノートの数字が古い**可能性をまず疑う
  （項目34と同じ型の事故。今回はノート側を訂正した）。
- 間接的な指標（選択状態・見た目）より、**壊れた条件そのもの**（値の重複）を見張るほうが確実。

   `backgroundColor` を見張っても `background-image` / `box-shadow` / `opacity` / `::after` で同じ結果になり、
   しかも `var()` だけで書けるので**色リテラル検査も原理的に反応しない**。
   面積で覆いを測るのは不可能と実測済み（健全時 ③は22%しか見えない）＝**既定値の固定allowlistで
   「壊れた条件そのもの」を見張る**のが唯一まともに機能する形。
→ **教訓【3回目】：CSSを末尾に足す形の変異は `cssRuleFor` 系が「後から足した規則を拾って `var()` を見失い」
   別件で赤くなる。これを「直っている」と誤認しかける。**今回 H（影）と I（透明度）で実際に踏みかけ、
   同じ規則に `var()` を書き戻した H2/I2 で測り直したら**完全に素通り**だった。
   **巻き添えの赤は成功ではない。赤くなった「項目名」まで必ず確認する。**
→ **教訓：件数が増えていても、古い検査がこっそり消えていないかは別に確かめる。**
   合計だけ見ていると「+15」に見えて実は「-3して+18」かもしれない。
